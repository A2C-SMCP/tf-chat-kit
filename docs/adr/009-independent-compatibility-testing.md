# ADR-009：独立项目与仓库内兼容性测试

- 状态：Accepted
- 日期：2026-07-30
- 补充：ADR-003 的 Gateway 边界与 ADR-008 的公开发布门禁

## 背景

tf-chat-kit 将作为更底层的公共能力被不同宿主接入。若发布依赖真实
TFRobotFront、TFRobotServer、Office Add-in 或 Tauri 项目的代码、构建环境、部署状态或 Jira
进度，Chat Kit 就无法独立演进和交付。反过来，如果完全不模拟这些接入形态，公共包的类型、
依赖、传输、生命周期和 UI 组合兼容问题又只能在下游暴露。

## 决策

- tf-chat-kit 的源码、构建、测试和发布不依赖任何外部项目仓库、源码路径、制品或任务状态。
- 每个公开声明支持的接入形态都必须在本仓库维护近似的契约型 mock 或版本化消费者。
- 仓库内兼容测试必须从待发布 tarball 或精确 Registry 版本安装公共入口，不得通过 workspace
  源码路径伪造可接入性。
- TFRobot 风格受控传输必须覆盖 DTO 校验、历史/实时、重复/乱序、unknown、断线、认证失败、
  会话隔离和资源释放。
- Front、Office 和 Tauri 风格消费者必须覆盖各自的依赖拓扑、peer 下界、宿主注入、实例隔离、
  命令链路和卸载清理。
- mock Feature Flag 必须验证新旧路径互斥、失败关闭、回滚和无残留连接；它是宿主集成协议的
  模型测试，不是生产灰度实现。
- 上述仓库内兼容矩阵是 `next` 与 `latest` 的发布硬门禁。
- 真实外部 E2E 可以从独立 workflow 或合规环境运行并写入兼容报告，但不成为 Chat Kit 构建、
  发布或 Epic 关闭的依赖。未运行时标记“未验证”；运行失败时明确记录兼容风险。
- 真实 E2E 暴露的 Kit 缺陷必须回流为本仓库 fixture、mock 或契约测试，确保问题可在不访问
  外部项目的情况下稳定复现。

## 影响

- `release/compatibility.json` 保留真实服务和真实宿主状态作为信息性兼容元数据，但发布许可只由
  仓库内 mock/消费者和包级质量门推导。
- 外部项目可以独立选择接入、灰度和退场节奏；Chat Kit 不拥有其 Feature Flag、路由、登录、
  部署或旧代码删除。
- 新增支持声明时，必须同时新增或扩展本仓库的近似消费者；仅提供真实环境截图或人工记录不足以
  建立长期兼容门禁。

## 未采用方案

- 真实宿主或真实服务通过后才允许 `latest`：会把底层项目发布绑定到外部项目进度。
- 只运行单元测试、不维护宿主拓扑 mock：无法发现 peer、打包、注入和生命周期兼容问题。
- 复制外部宿主源码或锁文件：会形成隐式分叉和反向依赖；只允许提取稳定行为、契约和版本范围。
